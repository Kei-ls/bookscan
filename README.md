# Bookscan

책이나 종이를 찍은 사진에서 페이지만 잘라내 스캐너로 뜬 것처럼 보정하고,
여러 장을 순서대로 묶어 PDF로 만드는 로컬 프로그램. vFlat 같은 문서 스캔 앱을
데스크톱에서 쓰는 형태다.

브라우저 UI로 동작하지만 **전부 내 PC 안에서만** 돈다. 사진이 밖으로 나가지 않는다.

## 실행

```
run.bat
```

처음 한 번은 가상환경과 의존성을 자동으로 설치한다(몇 분). 이후에는 바로 서버가
뜨고 브라우저가 열린다. 끄려면 콘솔 창에서 `Ctrl+C`.

옵션은 그대로 넘어간다:

```
run.bat --port 9000 --no-browser
```

> `run.bat`은 **CRLF 줄바꿈 + CP949 인코딩**으로 저장해야 한다. LF만 있으면 cmd가
> 괄호 블록 파싱에 실패하고, UTF-8로 저장하면 한글이 깨진다. 파일 안에서
> `chcp 65001`로 바꾸는 것도 안 된다 — cmd가 이후 줄의 바이트 위치를 잘못 잡아
> 엉뚱한 명령을 실행한다. `.gitattributes`에서 `*.bat -text`로 git의 변환을 막아 둔다.

직접 실행하려면:

```
.venv\Scripts\python.exe -m bookscan            # 기본 http://127.0.0.1:8765
.venv\Scripts\python.exe -m bookscan --port 9000 --no-browser
```

## 쓰는 순서

1. **사진 넣기** — `input` 폴더에 사진을 넣고 `폴더 가져오기`를 누르거나,
   파일을 창에 끌어다 놓거나, `파일 선택`으로 고른다.
   아이폰 HEIC 사진도 그대로 읽는다.
2. **결과 확인** — 썸네일이 뜬다. `확인 필요` 배지가 붙은 건 페이지 검출이
   애매했다는 뜻이니 열어서 손봐준다.
3. **상하 맞추기** — 글줄 방향(가로/세로)은 자동으로 맞지만 상하는 자동
   판별하지 않는다(아래 *처리 과정* 참고). 결과가 뒤집혀 있으면 목록 위
   **전체 180° 뒤집기**를 한 번 누른다. 같이 찍은 사진은 전부 같이 돌아간다.
4. **다듬기** — 카드를 더블클릭하면 편집 창이 열린다.
   - 모서리 네 점을 끌어서 페이지 영역 조정
   - 컬러 / 회색조 / 흑백 전환
   - 자동 회전 끄기, 수동 회전, 밝기, 대비
   - 펼침면 분할 방식과 책등 위치
   - 검출 모델 (사진 한 장만 다른 모델로 다시 검출)
   - 책 경계로 재단(배경 제거) 켜기·끄기
   - 곡면 펴기(dewarp) 켜기·끄기
5. **순서 맞추기** — 카드를 끌어서 옮기거나, 카드 위 `◀ ▶` 버튼으로 한 칸씩 이동.
6. **PDF 만들기** — 오른쪽 위 `PDF 만들기`. 만든 뒤 탐색기가 자동으로 열린다.

결과물은 `output/<프로젝트>/pages/`에 **읽는 순서대로** `0001.jpg`, `0002.jpg` …
로 저장된다. 순서를 바꾸면 파일 이름도 따라서 다시 매겨진다.

## 카메라로 바로 찍기

오른쪽 위 `카메라` → 장치 선택 → `연결`. 라이브 화면에 검출된 페이지 테두리가
겹쳐 보이고, `촬영` 버튼이나 **스페이스바**로 찍으면 바로 보정되어 목록에 붙는다.

> 아이폰을 웹캠으로 쓰려면 **Camo / Iriun / EpocCam** 같은 앱을 깔아 Windows
> 가상 카메라로 잡히게 해야 한다. Windows 11에는 macOS의 연속성 카메라 같은
> 기본 기능이 없다. 노트북 내장 웹캠은 그냥 목록에 뜬다.

## 처리 과정

```
원본 → (신경망 분할) → 페이지 검출 → 굽은 테두리 검출 → 원근/곡선 보정
     → 자동 회전 → 책 영역 재단 → 펼침면 분할 → 곡면 펴기 → 종이 비율 → 화질 보정
```

- **페이지 검출** (`detect.py`) — 성격이 다른 세 방법을 시도하고 공통 채점
  함수로 가장 좋은 걸 고른다. 윤곽선(보통), 밝기·채도 분할(어두운 배경),
  직선 교점(흰 책상 위 흰 종이). 전부 실패하면 사진 전체를 쓰고 낮은 confidence를
  달아 UI가 수동 보정을 유도한다.

  펼침면을 찍으면 **한쪽 페이지만 잡힌다.** 가운데 책등이 바깥 테두리만큼 또렷해서
  한 면짜리 사각형이 양면 전체보다 높은 점수를 받기 때문이다(실측: 한쪽 면 0.806점
  vs 전체 책 0.630점). 점수로는 이길 수 없어서 구조를 본다 — **비슷한 크기의
  사각형 둘이 겹치지 않고 딱 붙어 있으면 펼친 책**으로 보고 둘을 합친 사각형을
  후보에 넣는다.

- **검출 모델 선택** (`models/`) — 위 세 방법 말고 신경망을 쓸 수도 있다. 오른쪽 위
  `검출 모델`에서 고르고, 사진별로는 편집 창에서 따로 바꾼다.

  | | 코너 오차(합성 6장) | 특징 |
  |---|---|---|
  | `내장 알고리즘` (기본) | **3.2px** | 설치할 것 없음 |
  | `Document-Scanner` | 19.2px | 신경망 결과를 우선 신뢰. 가장 빠름 |
  | `내장 + 신경망` (권장) | **3.2px** | 양쪽 후보를 채점해 비교 + 신경망 실루엣으로 재단 |

  신경망은 [Saeed-Biabani/Document-Scanner](https://github.com/Saeed-Biabani/Document-Scanner)
  (MIT)의 U-Net을 쓴다. 아키텍처는 `models/docscanner.py`에 옮겨 놓았고 가중치는
  [Hugging Face](https://huggingface.co/ordaktaktak/Document-Scanner)에서 받는다(122MB,
  SHA-256 검증). torch는 선택 의존성이라 UI에서 `설치`를 눌러야 깔린다(CPU 전용
  인덱스에서 받는다 — 윈도우 기본 PyPI 휠은 CUDA가 딸려와 2GB가 넘는다).

  **신경망 후보를 특별대우하지 않는 것이 핵심이다.** 같은 채점 함수로 재고 이기면
  쓴다. 그래서 `내장 + 신경망`의 코너 오차가 내장과 **정확히 같다** — 합성 이미지
  6장에서 신경망 사각형은 한 번도 이기지 못했고(그 사진들은 모델의 학습 분포 밖이라
  단독으로는 114px까지 벌어진다) 채점이 전부 걸러냈다. 반대로 `Document-Scanner`
  모드는 채점을 건너뛰고 모델을 믿기 때문에 그만큼 위험하다.

  값이 있는 곳은 **사각형이 아니라 마스크** 쪽이다. 실사진에서 이 모델은 휜 책
  테두리를 사각형보다 잘 따라가고, 그 마스크를 아래 *책 영역 재단*의 실루엣으로
  그대로 넘긴다. 실측으로 배경을 5% 지우던 사진이 12%까지 올라갔다.

  > 이 체크포인트는 **확률을 0~1로 벌리지 못한다.** 실측한 모든 사진에서 출력이
  > 0.47~0.72 안에 뭉쳐 있었고 최댓값은 늘 0.724였다. 그래서 교과서적인 0.5로
  > 자르면 화면의 96~98%가 "문서"가 되어 마스크가 아무 일도 하지 않는다. 확률의
  > 절댓값이 아니라 분포 안에서의 상대 위치를 봐야 한다 — Otsu를 쓴다
  > (Otsu 114px < 원 저장소의 mean+std/2 방식 125px < 고정 0.5 244px).

- **굽은 테두리 검출** (`pagecurve.py`, `warp.curved_maps`) — 위 검출이 내놓는 건
  사각형인데, 펼친 책은 사각형이 아니다. 종이가 책등 쪽으로 말려 들어가면서 위/아래
  테두리가 활처럼 휘고, 사각형의 변은 그 활의 **현**이라 가운데로 갈수록 실제 종이에서
  멀어진다. 그래서 사각형을 씨앗으로만 쓰고 네 변을 각각 곡선으로 다시 잡는다.

  1. **어림잡기** — 책 실루엣 마스크가 있으면 변에 수직으로 깊게 훑는다. 마스크는 속이
     꽉 찬 도형이라 가짜 봉우리가 없어서, 얼마나 깊이 파고든 테두리든 한 번에 찾는다
     (펼침면의 책등 부근은 실측으로 높이의 12%까지 들어온다).
  2. **다듬기** — 그 곡선 위에 띠를 다시 얹고 이번엔 사진의 밝기 기울기로 정확한
     위치를 잡는다. 띠를 좁혀가며 두 번 반복하고, 후보 중 **경계 안팎의 밝기 단차가
     가장 큰 것**을 고른다.
  3. **확인** — 고른 자리의 단차가 충분한지 본다. 아니면 그 변을 통째로 버린다.

  마스크에 위치만 묻고 최종 판정은 사진에 맡기는 게 핵심이다. 마스크는 틀린다 —
  흰 책상 위 흰 종이에서는 GrabCut이 **종이 한가운데를 가로지르는 울퉁불퉁한 덩어리**를
  내놓는데, 그걸 믿으면 평평한 종이에 5%짜리 가짜 휘어짐이 생기고 그대로 펴면 멀쩡한
  페이지가 뒤틀린다. 3번 관문이 그런 마스크를 걸러낸다(종이 한가운데엔 넘을 단차가 없다).
  마스크 없이 기울기만으로도 동작하므로 재단을 꺼도 곡선 보정은 살아 있다.

  펴는 건 두 가지가 동시에 일어난다.

  - **모양** — 네 곡선을 직사각형의 네 변으로 보낸다. 바탕은 호모그래피를 깔고 곡선은
    거기서 벗어난 **잔차만** 얹는다. 겹선형 Coons 패치만 쓰면 원근을 풀지 못해서, 곧은
    사각형을 넣어도 호모그래피와 평균 48픽셀 어긋났다. 바탕을 깐 뒤에는 0.8픽셀이다.
  - **간격** — 격자를 균등하게 찍지 않는다. 원근에서 확대율은 방향을 가리지 않으므로
    **세로 자가 짧게 찍힌 곳은 가로도 같은 비율로 눌려 있다.** 그 역수만큼 늘려 주면
    책등 근처에서 뭉개진 글자 간격이 돌아온다. 글자를 보고 재는 `dewarp.py`와 달리
    **글자가 없어도 된다** — 사진이 한 면을 다 채워도 테두리만 보이면 잴 수 있다.

  휘어짐이 미미하면(현 길이의 0.8% 미만) 곡선으로 볼 이유가 없으므로 지금까지처럼
  호모그래피 한 장으로 끝낸다. **평평한 사진의 결과는 한 픽셀도 달라지지 않는다.**

  적용되면 찾아낸 곡선이 편집 창에 노란 선으로 나온다. 파란 사각형과 벌어진 만큼이
  사각형으로는 담지 못하던 부분이다.

  > 테두리만 보고서는 "책이 접혀서 왼쪽이 멀어진 것"과 "평평한 종이를 왼쪽에서
  > 비스듬히 찍은 것"을 구별할 수 없다. 둘 다 왼쪽 자가 짧게 나오기 때문이다. 이
  > 단계는 전부 접힘으로 본다. 위에서 내려찍는 보통의 책 사진에서는 그 가정이 맞지만,
  > 많이 비스듬한 사진에서는 결과가 실제보다 조금 갸름해진다.
  >
  > 이 한계는 아래 **종이 비율**로 없앨 수 있다. 판형을 알려주면 사라진다.

- **종이 비율** (`warp.fit_paper`) — 결과의 가로세로비를 **재는** 대신 **아는** 값으로
  못박는다. 편집 창의 `종이 비율`에서 A4·B5·Letter를 고르면 된다. 기본값
  `사진에서 잰 대로`는 아무것도 하지 않는다.

  이게 이득인 이유는, 이 파이프라인이 비율을 틀리는 방식이 정확히 여기서 고쳐지는
  종류이기 때문이다. 바로 위의 접힘·기울기 혼동은 **전역 배율 오차 하나**로 나타나서,
  판형을 알면 그 자유도가 통째로 사라진다. 반대로 국소 왜곡은 하나도 못 고친다.

  목표 비율은 하나가 아니라 셋이다. 세로 낱장(`r`), 가로로 누운 낱장(`1/r`), 그리고
  쪼개지 않은 펼침면(`2r` — 세로 낱장 둘이 나란히). 셋 중 잰 값에 가장 가까운 것으로
  스냅한다. 가로/세로만 보고 뒤집던 첫 판은 여기서 틀렸다. A4는 비율이 1/√2라
  `2r`과 `1/r`이 **우연히 같아서** 맞는 것처럼 보이는데, Letter는 1.545 대 1.294로
  크게 갈라진다(실제로 펼침면 오차를 0.038 → 0.114로 악화시켰다).

  한 축을 1.25배 넘게 늘려야 맞는다면 **비율이 아니라 다른 게 틀린 것**이다
  (검출 실패로 페이지가 가늘고 긴 띠가 됐다든가). 그럴 땐 건드리지 않고 이유를
  메모에 남긴다. 잘못 편 페이지는 안 편 페이지보다 나쁘다는 원칙이 여기서도 같다.

  분할이 **끝난 뒤 낱장에** 적용한다. 재단은 비율을 거의 안 바꾸지만(0.701 → 0.702)
  분할은 반으로 자르기 때문에(1.405 → 0.693), 워프 단계에서 못박아 봐야 뒤에서
  무너진다.

- **자동 회전** (`orient.py`) — 책을 옆으로 눕혀 찍으면 이후 단계가 전부 헛돈다.
  곡면 펴기는 글줄이 가로로 누워 있다고 보고 곡률을 재고, 펼침면 분할은 책등이
  세로로 서 있다고 보고 찾기 때문이다. 현재 방향과 90도 돌린 방향에서 각각
  본문 줄 수를 세어 많은 쪽을 택한다. 두 방향이 비슷하면 손대지 않는다.

  > **상하(180도)는 판별하지 않는다.** 글줄 안 잉크의 상하 비대칭으로 가려봤지만
  > 반증했다. 실제 사진에서는 정방향에서 일관되게 음수가 나왔는데 폰트를 바꿔
  > 렌더한 합성 페이지에서는 양수로 **부호가 반대**였다(규칙 적중 1/11). 틀린
  > 자동 회전은 안 한 것보다 나쁘다. 대신 한 번에 찍은 묶음은 상하가 모두 같으니
  > 목록 위 **전체 180° 뒤집기**로 한꺼번에 처리한다.
- **책 영역 재단** (`bookmask.py`, `booktrim.py`) — 펼친 책은 사각형이 아니다.
  바깥 테두리가 불룩하고 종이 뭉치 두께 때문에 위아래가 휘어 있어서, 직선 네 변으로
  감싸면 모서리에 책상·바닥이 딸려 들어온다. 펼침면을 반으로 쪼개면 그 배경이
  한쪽 페이지에 몰려 특히 눈에 띈다.

  검출된 사각형을 씨앗으로 GrabCut을 돌려 실제 실루엣을 딴 뒤, 그 위/아래/왼쪽/
  오른쪽 경계를 각각 곡선으로 보고 네 곡선이 출력 직사각형의 네 변이 되도록 다시
  매핑한다(Coons 패치). 사각형으로 잘라내면 휜 테두리와 직선 사이에 배경 쐐기가
  남으므로, 자르지 않고 **편다**.

  신경망 검출기를 켜면 GrabCut 대신 그 분할 마스크를 쓴다. 다만 **똑같은 검사를
  통과해야 한다** — 신경망도 틀린다. 색지 간지가 있는 사진에서는 그 페이지를 배경으로
  보고 책의 절반만 내놓는데, 그런 마스크는 면적 검사에 걸려 자동으로 GrabCut으로
  되돌아간다.

  **곡선 보정이 이미 테두리를 폈다면 이 Coons 패치는 건너뛴다.** 편 걸 또 펴면 두 번
  편 셈이 되고, 3500픽셀짜리 리샘플링만 한 번 더 낭비된다. 그때는 배경을 지우고 여백을
  잘라내는 일만 한다.

  GrabCut은 색 모델을 k-means로 초기화하고 그 k-means가 OpenCV의 전역 난수를 쓴다.
  씨를 고정하지 않으면 **같은 사진을 다시 처리할 때마다 결과가 달라진다** — 실제로
  어떤 사진이 실행마다 재단됐다 안 됐다 했다. `GRABCUT_SEED`로 고정해 둔다.

  씨앗을 바깥으로 넉넉히 열어두면 GrabCut이 어두운 책상을 책의 어두운 부분과 같은
  색으로 보고 바깥으로 자란다(실제로 겪었다). 그래서 바깥은 2%만 열고 안쪽으로만
  깎게 했다. 반대로 배경과 종이 색이 비슷하면 페이지 안쪽을 배경으로 오인하므로,
  **글자가 있는 곳은 절대 넘어오지 못하게** 막고 한 변에서 잘라낼 양도 10%로
  제한한다. 경계가 매끄럽지 않으면 기하 변형을 포기하고 배경만 종이색으로 지운다.

- **화질 보정** (`enhance.py`) — 조명 얼룩 제거가 핵심. 배경 조명장을 추정해
  **나눗셈**으로 정규화한다(조명은 곱셈으로 작용하므로 뺄셈이 아니다).
  채널별로 나누면 화이트밸런스가 덤으로 따라와 누런 종이가 흰색이 된다.
- **곡면 펴기** (`dewarp.py`) — 본문 텍스트 줄의 휘어짐을 재서 종이 표면 형상을
  역산하고 되편다. **잘못 편 페이지는 안 편 페이지보다 나쁘기 때문에** 안전장치가
  여러 겹 있다. 줄이 4개 미만이거나, 피팅이 나쁘거나, 줄마다 휘어짐이 제각각이거나,
  이미 평평하면 아무것도 하지 않고 원본을 그대로 통과시킨다.
- **펼침면 분할** (`spread.py`) — 책등 그림자(밝기 골짜기)와 잉크 공백을 함께 본다.
  양쪽에 본문이 비슷하게 있어야 하고 책등 그림자가 있어야 분할한다. 단면을 잘못
  쪼개는 쪽이 안 쪼개는 쪽보다 나쁜 실패이므로 애매하면 분할하지 않는다.

  > 색지에 흰 글자를 얹은 **간지(부 표지) 페이지**가 한쪽에 오면 그 페이지 전체가
  > '잉크 공백'으로 읽혀 책등 위치를 못 찾는다. 그런 사진은 편집 창에서
  > `펼침면 → 두 면 분할`로 지정하고 필요하면 책등 슬라이더로 위치를 잡아준다.

## 검증

합성 이미지로 회귀 테스트를 돌릴 수 있다. 깨끗한 페이지에 알려진 원근 왜곡 ·
곡률 · 조명 얼룩을 인위적으로 입혀 '가짜 사진'을 만들므로 정답을 알고 있다.

```
.venv\Scripts\python.exe tools\make_synthetic.py tests\synthetic   # 테스트 사진 생성
.venv\Scripts\python.exe tools\eval_detect.py                      # 코너 검출 오차
.venv\Scripts\python.exe tools\eval_dewarp.py                      # 곡면 펴기 + 안전장치
.venv\Scripts\python.exe tools\eval_curve.py                       # 굽은 테두리 + 곡선 보정 + 종이 비율
.venv\Scripts\python.exe tools\test_camera_path.py                 # 카메라 코드 경로
```

현재 상태: 검출 평균 코너 오차 **3.2px**(6개 케이스), 휘어진 페이지 직선성
**24~30% 개선**, 평평한 페이지는 손대지 않음. `내장 + 신경망`도 같은 3.2px
(신경망 후보를 채점이 전부 걸러낸다는 뜻이다).

곡선 보정은 따로 잰다. `make_synthetic.py`의 `bend`는 **테두리까지 휘는** 사진을
만든다(위의 `curl`은 페이지 안쪽 글자만 밀어서 실루엣이 반듯한 사각형으로 남는다).
평평한 페이지를 가로세로비를 아는 상태로 접었으니, 잘 폈다면 비율이 원래대로
돌아와야 한다.

| 사진 | 가로세로비 오차 (끔 → 켬 → +판형) | 글줄 휘어짐 (끔 → 켬) | 테두리 오차 |
|---|---|---|---|
| `bent_single` | 0.129 → 0.073 → **0.018** | 0.0012 → **0.0004** | **0.14%** |
| `bent_single_strong` | 0.146 → 0.121 → **0.018** | 0.0010 → **0.0004** | **0.17%** |
| `bent_spread` | 0.112 → 0.079 → **0.031** | 0.0024 → **0.0021** | 1.04% (아래 참고) |
| `bent_single_tilted` | 0.304 → 0.304 → **0.017** | 0.0012 → **0.0003** | **0.09%** |

`+판형`은 낱장 판형을 알려준 경우(`PageSettings.paper`)다. 남는 오차는 프리셋과 합성
페이지의 실제 비율 차이(A4 0.707 대 0.720 = 1.8%)라 이게 바닥이다. **테두리만으로는
못 고치는 한계가, 판형 한 줄로 사라진다.**

**테두리 오차**는 검출한 곡선을 정답 실루엣(`<name>_mask.png`)과 직접 견준 값이다.
결과 지표(비율·글줄)만 보면 중간 단계의 오차가 서로 상쇄돼 안 보인다. 실제로 곡선이
통째로 **25픽셀** 밀린 채 두 지표를 통과한 적이 있다. 원인은 `_stitch`가 이웃한 두
곡선의 끝점을 **평균** 낸 것이었다 — 위 곡선은 모서리의 y를 알고 왼쪽 곡선은 x를
아는데 둘을 섞으니, 아는 값이 모르는 값 쪽으로 절반 끌려가고 그 오차가 램프를 타고
곡선 전체로 번졌다. 두 끝 접선의 **교점**으로 바꾸니 25px → 1.3px이 됐다.

> 그 25px 편향이 늘리는 양을 줄여서, 접힘/기울기 혼동으로 인한 과다 확대와 서로
> 상쇄되고 있었다. 그래서 테두리를 바로잡자 `켬` 열의 비율 오차는 오히려 커졌다
> (0.025 → 0.073). 바로잡힌 건 잰 값 쪽이다 — 늘림 배율은 정답과 1.316 대 1.300,
> 1.336 대 1.340으로 맞고, 글줄 휘어짐은 모든 케이스에서 좋아졌으며, `+판형`을
> 주면 네 케이스 전부 역대 최저(≤0.031)다. 실사진에서 곡선 바깥에 남던 배경도
> 5.1% → 1.0%, 8.0% → 1.6%로 줄었다.

실사진에서도 값이 모인다. 같은 책을 찍은 10장의 잰 비율이 ±12% 흩어져 있었는데,
B5로 못박으면 전부 0.704가 된다. 펼침면을 쪼갠 두 반쪽이 서로 다른 크기로 나오는
것(0.668 대 0.691)도 같이 해결된다.

> **펼침면 테두리는 아직 1% 벗어난다.** 책등의 **국소 주름**을 3차식이 담지 못한다.
> 차수를 올리면 여기는 0.11%까지 좋아지지만 단면이 0.17% → 2.27%로 망가진다(양 끝을
> 빼고 맞춘 고차식이 모서리에서 날뛴다). 전역 다항식이 아니라 구간별 표현이 필요하다는
> 신호다. `curve_truth.json`의 `boundary_tolerance`로 현재 값을 고정해 뒀다.

> 글줄 휘어짐은 `dewarp._fit_curves`로 재면 **안 된다.** 그건 줄들의 휘어짐을 평균
> 내는데, 이 왜곡에서는 가운데 줄을 기준으로 위쪽 줄과 아래쪽 줄이 서로 반대로 휘어
> 평균이 0에 가깝게 상쇄된다(실제로 상쇄돼서 값이 좋아 보이는 착시를 한 번 겪었다).
> 줄마다 따로 재서 부호를 없앤 뒤 평균 낸다. 덧붙이면 이 상쇄가 곧 `dewarp.py`가 이
> 왜곡을 못 잡는 이유이고, 글줄이 아니라 테두리를 봐야 하는 근거다.

## 알려진 제약

- 상하 반전(180°) 자동 판별은 안 한다. 휴리스틱으로 시도했다가 반증했고
  (위 *처리 과정* 참고) 제대로 하려면 OCR이 필요하다. 목록 위
  `전체 180° 뒤집기`로 묶음 단위로 처리한다.
- 원본은 `originals/`에 JPEG로 다시 인코딩해 보관한다. 한 세대 손실이 있고
  검출 결과가 원본 파일과 미세하게 달라질 수 있다.
- 곡면 펴기는 본문 텍스트가 있는 페이지에서만 동작한다. 사진이나 도판만 있는
  페이지는 기준으로 삼을 텍스트 줄이 없어 그냥 통과시킨다.
- 실제 카메라 장치 열기는 이 개발 PC에 카메라가 없어 실물 검증을 못 했다.
  코드 경로는 가짜 프레임 주입으로 확인했다.
- 신경망 검출기는 **내장 알고리즘보다 나은 결과를 보장하지 않는다.** 실사진 4장으로
  재본 결과 배경은 더 지웠지만(5%→12%) 마스크가 페이지를 파고들어 종이색 자국이
  남는 사진도 있었다. 그래서 기본값은 `내장 알고리즘`이고, 사진별로 바꿀 수 있게 했다.
- 굽은 테두리 보정은 **테두리가 사진 안에 다 보여야** 동작한다. 페이지를 가까이서
  찍어 테두리가 화면 밖으로 나가면 곡선을 찾지 못하고 지금까지의 원근 보정으로
  돌아간다(그런 사진에서 억지로 잡아낸 '테두리'는 본문 블록의 경계라, 그대로 펴면
  오히려 망가진다. 밝기 단차 검사가 그걸 막는다).
- 많이 비스듬하게 찍은 사진에서는 곡선 보정이 결과를 실제보다 갸름하게 만든다.
  테두리만으로는 접힘과 기울기를 구별할 수 없기 때문이다(위 *처리 과정* 참고).
  `tools/eval_curve.py`의 `bent_single_tilted`가 그 경우로, 알려진 한계로 표시해 뒀다.
  **판형을 알려주면 이 한계는 사라진다** (오차 0.348 → 0.019). 편집 창의 `종이 비율`.
- 종이 비율 맞추기는 전역 배율 하나만 바로잡는다. 페이지 안쪽이 국소적으로 일그러진
  건 그대로 남는다. 그건 곡선 보정과 곡면 펴기의 몫이다.
- 가중치는 남이 올린 `.pth`, 즉 pickle이다. `torch.load(weights_only=True)`로 텐서만
  읽고 SHA-256을 검증한다. 그래도 출처를 확인하고 쓰는 게 좋다.
